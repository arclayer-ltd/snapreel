# Snapreel Pro backend: runbook

How the hosted-links backend is put together and how to run it. The API contract is [API.md](API.md); this file
is about operating it. Written 20 November 2026.

## What runs where

| Piece | Where |
|---|---|
| Database, sign-in, video storage | Supabase project **Snapreel**, ref `jaajkutdglblwtpfcgag`, us-east-1, org SourceBD (Pro plan, micro compute, $10/month) |
| API, watch pages, dashboard, site, Lock Screen relay | Next.js app in `web/`, Vercel project `snapreel-push` (team `dev-34969213`), domains snapreel.video and www |
| Email | Resend, domain `snapreel.video` (us-east-1), sender `Snapreel <hello@snapreel.video>`, replies to `support@snapreel.video` |
| Push | APNs with the team key "Arclayer Push" (`APNS_*`): Live Activity relay and alert pushes |
| DNS | Hostinger hPanel (nameservers `*.dns-parking.com`) |

Server code lives in `web/lib/server/` (shared) and `web/app/api/` (routes). The functions the watch page and
dashboard call during SSR are in `web/lib/server/queries.ts`; the signed-in web user comes from
`getSessionUser()` in `web/lib/server/session.ts`. `web/proxy.ts` (Next 16's middleware) refreshes web sessions
on `/app`, `/login` and `/v`.

## Supabase settings made in the dashboard

- Created with "Grant API access to new tables automatically" **off** and "Enable RLS automatically" **on**. Every
  grant is in the migrations; `anon` has none.
- Auth → URL Configuration: Site URL `https://snapreel.video`; redirect URLs `https://snapreel.video/**`,
  `https://www.snapreel.video/**`, `http://localhost:3000/**`.
- Auth → Providers → Email: email OTP length **6**, expiry **600 s**, magic links and OTP on, confirm email on.
- Auth → Rate Limits: emails sent per hour **100** (the default 2 would block sign-ins).
- Auth → Hooks: **Send Email** hook, HTTPS, `https://snapreel.video/api/auth/send-email`, secret in
  `SUPABASE_AUTH_HOOK_SECRET`. While it's enabled Supabase's own templates aren't used.
- Auth → Providers → Apple: enabled, client IDs `co.arclayer.snapreel,co.arclayer.snapreel.web` (native and
  web). "Secret Key (for OAuth)" holds the web client secret: see "Apple client secret" below.
- Auth → Performance: connection allocation **percentage** (17%).
- Storage → Settings: global file size limit **2048 MB** (the `videos` bucket allows 2 GB; the spend cap caps
  uploads at 50 GB, more than enough).

## Migrations

`supabase/migrations/*.sql`, named with the version Supabase recorded, so `supabase migration list` matches:

| Version | What |
|---|---|
| 20261119232438 schema | enums, tables, indexes, `private.rate_limits` |
| 20261119232452 rls | grants and policies |
| 20261119232520 functions | `handle_new_user` trigger, `is_pro`, `active_link_count`, `rate_limit_hit`, `record_view`, `video_stats` |
| 20261119232546 storage | private `videos` bucket and owner-folder policies |
| 20261119233239 advisor_fixes | `rls_auto_enable()` locked down, explicit server-only policies |
| 20261119233521 device_token_check | fixes a regex Postgres can't run (`{32,400}`) |
| 20261120001418 prune_rate_limits | cleanup helper for the cron |

To add one: write the file, apply it (Supabase MCP `apply_migration`, or `supabase db push` from a linked
checkout), rename the file to the recorded version (`list_migrations`), then:

1. `get_advisors` security and performance. Security must be empty. "Unused index" (INFO) is expected until there
   is traffic.
2. Regenerate `web/lib/server/database.types.ts` (MCP `generate_typescript_types`; keep the header comment and the
   short `Tables`/`Enums` helpers at the bottom).
3. Run `supabase/tests/rls_checks.sql` (SQL editor or MCP `execute_sql`). It seeds two users, runs 72 checks as
   `anon`, user A, user B and `service_role`, and always ends by raising an exception, so nothing is kept. The
   message starts with `RLS CHECKS: n passed, m failed`.

## Deploy

The Hobby plan rejects deployments whose git commit author isn't `arclayers <dev@arclayer.co>`, so deploy from a
copy of `web/` outside git:

```bash
D=/path/outside/git/snapreel-web            # once: vercel link --yes --project snapreel-push --scope dev-34969213
rsync -a --delete --exclude node_modules --exclude .next --exclude '.env*' --exclude .vercel web/ "$D/"   # or: tar with the same excludes
cd "$D" && vercel deploy --prod --scope dev-34969213
```

The project's framework is set to Next.js (`web/vercel.json` says so too); Node 26.x. The owner's mobile carrier
can't reach Vercel's 64.29.17.x and 216.198.79.3/.131, which is what `*.vercel.app` preview URLs resolve to, so
test previews with `--resolve <host>:443:76.76.21.21`. snapreel.video's A records stay on 216.198.79.1 and
76.76.21.21.

### First production cutover (replacing the old static relay)

Before the switch the relay answered, for a made-up token, through both A-record IPs:
`502 {"apns":400,"apnsId":"<uuid>","reason":"BadDeviceToken"}` (`application/json; charset=utf-8`), and `GET`
gave `405 {"error":"POST only"}`. After deploying, check it's identical:

```bash
for ip in 216.198.79.1 76.76.21.21; do
  curl -sS --resolve snapreel.video:443:$ip -X POST -H 'content-type: application/json' \
    --data '{"token":"00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff","event":"end","contentState":{"phase":"stopped"}}' \
    https://snapreel.video/api/live-activity -w '  %{http_code}\n'
  curl -sS --resolve snapreel.video:443:$ip https://snapreel.video/api/health -w '  %{http_code}\n'   # {"ok":true,"configured":true}
done
curl -sS https://snapreel.video/.well-known/apple-app-site-association
bash scripts/pro-smoke.sh            # all checks, including the sign-in email through the hook
```

Locally (`next start` with a throwaway APNs key) every validation response of the ported relay was byte-for-byte
the same as the old one, and the APNs call went through end to end. Production passed these checks on 2026-11-20
(both IPs answered the same `BadDeviceToken` and `405` as before; `pro-smoke.sh` 91/91), and `server/push/` was
deleted.

`vercel env pull` can't read the production secrets (they're marked sensitive and come back as placeholders).
Run the smoke test with the development values instead, which are the same: `vercel env pull .env.smoke
--environment development`, then `ENV_FILE=.env.smoke bash scripts/pro-smoke.sh`, and delete the file.

## Cron

`web/vercel.json` schedules `GET /api/cron/daily` at 04:17 UTC (Hobby allows one run a day). It:
- marks uploads with no progress for 48 hours `failed` (the watch page says so);
- deletes the files of failed uploads after 7 days and of links 30 days past their expiry, keeping a tombstone;
- purges tombstones 30 days after the link stopped (the slug then reads "not found");
- expires subscriptions a day past `expires_at` that Apple never told us about;
- clears rate-limit windows older than a day and alert dedupe rows older than 90 days.

Run it by hand: `curl -H "Authorization: Bearer $CRON_SECRET" https://snapreel.video/api/cron/daily`.

## Sign-in email (Send Email hook)

Supabase Auth → `POST /api/auth/send-email` with a Standard Webhooks signature (`webhook-id`,
`webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">`, key = the base64 part
of `v1,whsec_…`). The route checks the signature (5-minute window), sends the 6-digit code with Resend and answers
`{}`; on failure it answers `{error: {http_code, message}}` and Supabase reports the error to the app. Email
change sends a code to both addresses. To rotate the secret: Auth → Hooks → Send Email → generate a new secret,
copy it, `vercel env add SUPABASE_AUTH_HOOK_SECRET … --force` in all three environments, redeploy.

## Apple

- **StoreKit 2 and App Store Server Notifications V2.** `web/lib/server/jws.ts` checks the x5c chain to the pinned
  Apple Root CA - G3 (`web/lib/server/certs/AppleRootCA-G3.cer`, SHA-256
  `63:34:3A:BF:…:3E:91:79`), Apple's marker OIDs, validity dates and the ES256 signature. Then
  `appstore.ts` checks the bundle ID, the product and (for `/api/purchases/verify`) that `appAccountToken` is the
  signed-in user's ID. Notifications (URL set in App Store Connect for production and sandbox:
  `https://snapreel.video/api/appstore/notifications`) update `subscriptions`. `node scripts/jws-selftest.mjs`
  exercises the verifier with a throwaway chain (11 checks).
- **Account deletion** revokes Sign in with Apple when the app sends a fresh `appleAuthorizationCode`: the
  server mints a 5-minute client secret from `SIWA_*`, exchanges the code and revokes the refresh token.
- **Apple client secret (every 6 months).** Web sign-in through Supabase's Apple provider needs a client-secret
  JWT for the Services ID `co.arclayer.snapreel.web`, and Apple caps it at 6 months. To renew (do it after about 5
  months; the script prints the expiry date):

  ```powershell
  node scripts/siwa-client-secret.mjs | clip
  ```

  Then Supabase → Authentication → Sign In / Providers → Apple → "Secret Key (for OAuth)" → paste → Save, and
  clear the clipboard. The script reads `~/.appstoreconnect/siwa/siwa.env` and the `.p8` it names. The first secret
  has not been pasted yet (an owner step). Native sign-in in the app doesn't need it.

## Smoke tests

```bash
bash scripts/pro-smoke.sh                           # against https://snapreel.video
RESOLVE_IP=76.76.21.21 bash scripts/pro-smoke.sh    # pin one Vercel IP
BASE=http://localhost:3000 bash scripts/pro-smoke.sh   # a local `next start`; skips the two production-only checks
```

It needs curl, ffmpeg, node and `web/.env.local`. It runs about 90 checks:
- it makes two throwaway users at Resend's test inbox (`delivered+smoke-…@resend.dev`) and signs them in with
  email codes;
- it makes a link, uploads an ~8 MB video plus poster and preview with TUS in 6 MB chunks, and marks it ready;
- it covers the public watch flow, password, expiry, view beacons, comments, the honeypot, reactions, a report,
  Free and Pro insights, isolation between the users, the Pro gates, block and delete, devices, forged JWS, cron
  auth, stopping the link and deleting both accounts.

It deletes what it made, even when a step fails, and it removes leftovers of runs killed more than 15 minutes
before. One real email goes out: the test report to support@snapreel.video ("Automated smoke test … Please
ignore."). Last result: 89 passed, 0 failed, against the live Supabase project through a local `next start`
(20 November 2026).

## Takedowns

A report arrives at support@snapreel.video and in `public.reports`. To take a video down without the owner, call
the same code the owner's "Stop sharing" uses: in the SQL editor, find it with
`select id, owner_id, slug from videos where slug = '<slug>';`; delete its files in Storage → videos →
`<owner_id>/<id>/`; then `update videos set deleted_at = now(), title = '', transcript = null, cta = null,
password_hash = null where id = '<id>'; delete from views where video_id = '<id>'; delete from comments where
video_id = '<id>'; delete from reactions where video_id = '<id>';` and close the report with
`update reports set resolved_at = now() where video_id = '<id>';`. The link then says "removed".
