# Snapreel Pro backend: runbook

How the hosted-links backend is put together and how to run it. The API contract is [API.md](API.md); this file
is about operating it. Written 20 November 2026.

## What runs where

| Piece | Where |
|---|---|
| Database, sign-in, video storage | Supabase project **Snapreel**, ref `jaajkutdglblwtpfcgag`, us-east-1, org SourceBD (Pro plan, micro compute, $10/month) |
| API, watch pages, dashboard, site, Lock Screen relay | Next.js app in `web/`, Vercel project `snapreel-push` (team `dev-34969213`), domains snapreel.video and www |
| Email | Resend, domain `snapreel.video` (us-east-1), sender `Snapreel <hello@snapreel.video>`, replies to `support@snapreel.video` |
| Push | APNs with the team key "Arclayer Push" (`APNS_*`): Live Activity relay and alert pushes |
| DNS | Hostinger hPanel (nameservers `*.dns-parking.com`) |

Server code lives in `web/lib/server/` (shared) and `web/app/api/` (routes). The functions the watch page and
dashboard call during SSR are in `web/lib/server/queries.ts`; the signed-in web user comes from
`getSessionUser()` in `web/lib/server/session.ts`. `web/proxy.ts` (Next 16's middleware) refreshes web sessions
on `/app`, `/login` and `/v`.

To add one: write the file, apply it (Supabase MCP `apply_migration`, or `supabase db push` from a linked
checkout), rename the file to the recorded version (`list_migrations`), then:

1. `get_advisors` security and performance. Security must be empty. "Unused index" (INFO) is expected until there
   is traffic.
2. Regenerate `web/lib/server/database.types.ts` (MCP `generate_typescript_types`; keep the header comment and the
   short `Tables`/`Enums` helpers at the bottom).
3. Run `supabase/tests/rls_checks.sql` (SQL editor or MCP `execute_sql`). It seeds two users, runs 74 checks as
   `anon`, user A, user B and `service_role`, and always ends by raising an exception, so nothing is kept. The
   message starts with `RLS CHECKS: n passed, m failed`.

copy of `web/` outside git:

```bash

cd "$D" && vercel deploy --prod --scope dev-34969213
```

## Cron

`web/vercel.json` schedules `GET /api/cron/daily` at 04:17 UTC (Hobby allows one run a day). It:
- repairs links still `uploading` or `failed` whose video is stored in full (only the app's last call was lost), and
  clears empty poster and preview files;
- marks uploads with no progress for 48 hours `failed` (the watch page says so; the phone can still finish them);
- deletes the files of failed uploads after 30 days and of links 30 days past their expiry, keeping a tombstone;
- purges tombstones 30 days after the link stopped (the slug then reads "not found");
- expires subscriptions a day past `expires_at` that Apple never told us about;
- clears rate-limit windows older than a day and alert dedupe rows older than 90 days.

Run it by hand: `curl -H "Authorization: Bearer $CRON_SECRET" https://snapreel.video/api/cron/daily`. With
`?repair=<user id>` it only repairs that person's links, at once.

## Uploads

How a recording gets from the phone to storage (`Snapreel/Services/Cloud/Uploader.swift`, `WebPreparer.swift`), and why.

**Transport: S3 multipart through Storage's S3 endpoint, with the person's own session token.** No new key: the access key
is the project ref and the secret the public `anon` key (`CloudConfig.anonKey`; publishable keys aren't accepted there yet,
github.com/supabase/storage/issues/750); the session token decides what may be touched, so the bucket's policies apply
(another person gets 403). Measured on 25 November 2026 from a PC on the owner's 4G hotspot in Bangladesh, same hour:

| File | TUS, 6 MB chunks | TUS, one request | S3, 1 at a time | S3, 3 at a time | S3, 6 at a time |
|---|---|---|---|---|---|
| 20 MB | 27.5 s (0.73 MB/s) | 30.5 s (0.66) | 28.1 s (0.71) | 31.5 s (0.63) | 40.1 s (0.50, one reset) |
| 170 MB | 384 s (0.44, one drop) | | | 210 s (0.81) | |
| 520 MB, connection cut every 90 s | | | | 863 s (0.60): finished, 27 pieces sent twice | |

One connection already fills this uplink, so parallel pieces are not what makes it faster: the differences between the
columns are mostly the radio from one minute to the next, and six at a time is worse.

What decided it is not the speed of one good minute but what happens on a phone:

| | TUS | S3 multipart | signed upload URL |
|---|---|---|---|
| With the app suspended | one chunk, then iOS must wake the app for the next, when it finds it convenient | the pieces are queued ahead | one request for the whole file |
| A dropped connection | iOS repeats the old chunk at the old offset: 409, the app must be woken | iOS repeats that piece (5 MB) by itself | the whole file again |
| A lost answer | ask for the offset | send the piece again, or nothing: its ETag is its MD5 | send everything again |
| Order | strictly one after another, from the start | any, so what is encoded goes up while the rest is being made, and the index goes last | one file, when it is finished |
| Valid for | the token's hour | the token's hour (a new token works with the same upload) | 2 hours |

Signatures are in the query string: a header-signed request is refused when its date is 15 minutes old
(`RequestTimeTooSkewed`), and a piece can wait longer than that. Unfinished uploads are aborted by Storage after 24 hours; the
app then starts that file again. If the `anon` key is ever switched off, S3 answers `SignatureDoesNotMatch` or
`InvalidAccessKeyId` and the app carries on with TUS by itself.

**What the answers mean** (`UploadAnswer.swift`; each was provoked against the live project, `scripts/s3-upload.mjs` and
`pro-smoke.sh` check most of them):

| Answer | Meaning | The app |
|---|---|---|
| `AccessDenied`, `"exp" claim timestamp check failed`: 400 from TUS and REST, 403 from S3 (checked with a token left to run out for an hour; the same multipart upload goes on with a new one); 400 `ExpiredToken` (the signature's own time is over); 401 | the token ran out | refreshes once, drops transfers with the old token, goes on |
| 409 `The resource already exists` / `KeyAlreadyExists` | the object is there. **TUS says this for ever when `x-upsert: true` is missing from the `PATCH`, even for a new upload**: that was build 47's endless loop | compares sizes: finished, or replaced |
| 409 `Upload-Offset conflict` | TUS is at another offset | asks (`HEAD`), goes on from there |
| 404 `NoSuchUpload` | finished earlier, aborted, or over 24 hours old | looks at the stored size: finished, or starts the file again (4 times at most) |
| 400 `InvalidPart`, `EntityTooSmall` | the list doesn't match | starts the file again |
| 403 `AccessDenied` (row-level security) | not allowed | new token twice, then stops |
| 403 `SignatureDoesNotMatch`, `InvalidAccessKeyId` | the S3 key is refused | TUS |
| 403 `RequestTimeTooSkewed` | the phone's clock is wrong | signs with the server's time |
| 423, 429, 5xx, no answer | busy | pauses 2 s to 2 min, 10 times at most, then Try again |
| no connection | | waits for it; a connection that keeps failing: 30 tries, then Try again |

**Background.** Three pieces are under way while Snapreel is open (one already fills a 4G uplink; more only lose more when
it drops). When it leaves the screen the rest is handed to the background URLSession: iOS's own process sends them with the
app suspended, closed by iOS, or the phone locked. Over HTTP/2 that process sends everything it was given **at the same time**
(20 of 20 in a probe on iOS 16.4, whatever `httpMaximumConnectionsPerHost` says), and a dropped connection loses all that was
under way. So it gets about two minutes' worth at once (30 to 150 MB, by the speed just measured) and the rest with
`earliestBeginDate`s, for at most 40 minutes ahead (a token lives an hour). Back in Snapreel the waiting ones are taken back and
go three at a time. Pieces started later, by an app in the background, are sent at iOS's discretion, which is why they are
written ahead and handed over first. Swiping Snapreel away in the app switcher stops them (iOS does that); they carry on at the
next launch. Preparing needs Snapreel running: about half a minute after it leaves the screen, then it stops, keeps what is
encoded, and goes on when Snapreel is open (or when iOS grants a processing task, `co.arclayer.snapreel.uploads.finish`).

**The web copy.** `WebPlan` picks: copied as it is (H.264, fits, at most a quarter over the target) or encoded in hardware in
stretches of 10 s. Targets: camera 5 Mbit/s at 1080p, 2.6 at 720p; screen recordings 2.6 and 1.35 (mostly still, sharp
edges), by pixels to the power 0.8; less when two hours must fit in 2 GB. Re-encoding a recording that is already near its
target would save little, cost minutes with Snapreel open, and blur text once more. `WebMovieFile` writes the MP4 itself:
room for the index is reserved at the start and filled last, so every other byte is final once written and can go up at
once; no second copy on a full phone; `prepare.json` and `samples.bin` let it carry on at the last stretch. Anything it can't
do (and any file that doesn't pass the check at the end) goes through Apple's exporter.

## Sign-in email (Send Email hook)

Supabase Auth → `POST /api/auth/send-email` with a Standard Webhooks signature (`webhook-id`,
`webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">`, key = the base64 part
of `v1,whsec_…`). The route checks the signature (5-minute window), sends the 6-digit code with Resend and answers
`{}`; on failure it answers `{error: {http_code, message}}` and Supabase reports the error to the app. Email
change sends a code to both addresses. To rotate the secret: Auth → Hooks → Send Email → generate a new secret,
copy it, `vercel env add SUPABASE_AUTH_HOOK_SECRET … --force` in all three environments, redeploy.

## Apple

- **StoreKit 2 and App Store Server Notifications V2.** `web/lib/server/jws.ts` checks the x5c chain to the pinned
  Apple Root CA - G3 (`web/lib/server/certs/AppleRootCA-G3.cer`, SHA-256
  `63:34:3A:BF:…:3E:91:79`), Apple's marker OIDs, validity dates and the ES256 signature. Then
  `appstore.ts` checks the bundle ID, the product and (for `/api/purchases/verify`) that `appAccountToken` is the
  signed-in user's ID. Notifications (URL set in App Store Connect for production and sandbox:
  `https://snapreel.video/api/appstore/notifications`) update `subscriptions`. `node scripts/jws-selftest.mjs`
  exercises the verifier with a throwaway chain (11 checks).
- **Account deletion** revokes Sign in with Apple when the app sends a fresh `appleAuthorizationCode`: the
  server mints a 5-minute client secret from `SIWA_*`, exchanges the code and revokes the refresh token.
- **Apple client secret (every 6 months).** Web sign-in through Supabase's Apple provider needs a client-secret
  JWT for the Services ID `co.arclayer.snapreel.web`, and Apple caps it at 6 months. To renew (do it after about 5
  months; the script prints the expiry date):

  ```powershell
  node scripts/siwa-client-secret.mjs | clip
  ```

  Then Supabase → Authentication → Sign In / Providers → Apple → "Secret Key (for OAuth)" → paste → Save, and
  clear the clipboard. The script reads `~/.appstoreconnect/siwa/siwa.env` and the `.p8` it names. The first secret
  has not been pasted yet (an owner step). Native sign-in in the app doesn't need it.

## Smoke tests

```bash
bash scripts/pro-smoke.sh                           # against https://snapreel.video
RESOLVE_IP=76.76.21.21 bash scripts/pro-smoke.sh    # pin one Vercel IP
BASE=http://localhost:3000 bash scripts/pro-smoke.sh   # a local `next start`; skips the two production-only checks
BASE=https://<preview>.vercel.app BYPASS_HEADER_FILE=<file> ENV_FILE=.env.smoke bash scripts/pro-smoke.sh   # a preview
```

A preview deployment is behind Deployment Protection. `BYPASS_HEADER_FILE` is a private file holding one line,
`x-vercel-protection-bypass: <secret>`, with the project's "Protection Bypass for Automation" secret (Vercel →
snapreel-push → Settings → Deployment Protection, the same one `vercel curl` uses). The script sends it only to
`$BASE`, never prints it; delete the file afterwards. On 20 November 2026 the preview of branch
`claude/silly-swirles-fb25d2` passed 110 checks, 0 failed (the two production-only checks skipped).

It needs curl, ffmpeg, node and `web/.env.local`. It runs about 90 checks:
- it makes two throwaway users at Resend's test inbox (`delivered+smoke-…@resend.dev`) and signs them in with
  email codes;
- it makes a link, uploads an ~8 MB video plus poster and preview with TUS in 6 MB chunks, and marks it ready;
- it covers the public watch flow, password, expiry, view beacons, comments, the honeypot, reactions, a report,
  Free and Pro insights, isolation between the users, the Pro gates, block and delete, devices, forged JWS, cron
  auth, stopping the link and deleting both accounts;
- it checks the comment word filter (a matching comment is held, hidden from the public activity, shown to the owner,
  can't be replied to or approved by another user, then approved and deleted) and "Don't count my views" (a second
  browser opts out, watches it all, and leaves no view row, keeping its `sr_vs`).

It deletes what it made, even when a step fails, and it removes leftovers of runs killed more than 15 minutes
before. One real email goes out: the test report to support@snapreel.video ("Automated smoke test … Please
ignore."). Last result: 89 passed, 0 failed, against the live Supabase project through a local `next start`
(20 November 2026).

## Comment word filter

`web/lib/server/moderation.ts` holds a short list of slurs and strong abuse (App Review guideline 1.2). A viewer's
comment whose name or text matches is stored with `comments.held = true`: public activity leaves it out, the poster
is told it waits for the owner, and the owner's alert says only that a comment is waiting. The owner approves
(`POST /api/comments/{id}/approve`) or deletes it in the dashboard or the app. To change the list, edit `STEMS` there
and redeploy; keep it short, since every match costs the owner a review. Before this filter, matching words were
masked with asterisks; comments stored that way stay as they are.

To see what's waiting across all owners: `select c.id, v.slug, c.author_name, c.body, c.created_at from comments c
join videos v on v.id = c.video_id where c.held and c.deleted_at is null order by c.created_at desc;`.

## Takedowns

A report arrives at support@snapreel.video and in `public.reports`. To take a video down without the owner, call
the same code the owner's "Stop sharing" uses: in the SQL editor, find it with
`select id, owner_id, slug from videos where slug = '<slug>';`; delete its files in Storage → videos →
`<owner_id>/<id>/`; then `update videos set deleted_at = now(), title = '', transcript = null, cta = null,
password_hash = null where id = '<id>'; delete from views where video_id = '<id>'; delete from comments where
video_id = '<id>'; delete from reactions where video_id = '<id>';` and close the report with
`update reports set resolved_at = now() where video_id = '<id>';`. The link then says "removed".
